# Обновление и откат

Что изменилось в новой версии, написано в [CHANGELOG.md](../CHANGELOG.md). Данные при обновлении не переносятся и не пересоздаются: новая версия открывает ту же базу и при запуске сама дописывает в неё новые таблицы и поля (миграции).

## Перед обновлением

Сделайте свежую копию, чтобы было к чему вернуться:

- **сервер:** в папке МедКонтроля

  ```bash
  docker compose exec backup bash /backup-loop.sh once
  ```

  Копия ляжет в `BACKUP_DIR`, в папку с датой и временем в имени. По умолчанию `BACKUP_DIR` это `medcontrol-backups` рядом с папкой кода. В версии 0.2.0 и раньше это `backups` внутри папки с кодом: такие копии нужно перенести, см. [«С версии 0.2.0 или раньше»](#с-версии-020-или-раньше);
- **настольная версия:** «Настройки → Архив всех данных → Скачать архив».

## С версии 0.2.0 или раньше

Три отличия, о которых стоит знать до обновления.

**Копии лежали внутри папки с кодом.** В версии 0.2.0 и раньше ночные копии по умолчанию ложились в `backups` внутри папки МедКонтроля, теперь в `medcontrol-backups` рядом с ней. Копия, сделанная перед обновлением, тоже лежит в старом месте. Новая версия туда не смотрит, а если удалить старую папку с кодом, копии пропадут вместе с ней. Если в `.env` нет строки `BACKUP_DIR`, перенесите копии до первого запуска новой версии:

```bash
# код через git: из папки с кодом
mv backups ../medcontrol-backups
# код из ZIP: из папки, в которой лежат старая и новая папки с кодом
mv старая-папка/backups medcontrol-backups
```

На Linux копии принадлежат root, перед `mv` понадобится `sudo`. Если папка `medcontrol-backups` уже есть, перенесите в неё папки с датами: `mv backups/20* ../medcontrol-backups/`.

Если в `.env` есть строка `BACKUP_DIR`, копии лежат там, где она указывает, и новая версия продолжит складывать их туда же. Строка `BACKUP_DIR=./backups` была в примере `.env` версии 0.2.0 и по-прежнему означает папку внутри кода. При обновлении через git с ней ничего переносить не нужно. При обновлении из ZIP это уже папка внутри новой копии кода, поэтому перенесите `backups` из старой папки в новую.

**Проект Docker назывался по папке.** В версии 0.2.0 и раньше имя проекта Docker бралось из имени папки с кодом, теперь оно всегда `medcontrol`. Если папка и так называется `medcontrol` (как после `git clone` без своего имени), ничего не меняется. Если иначе, например `medcontrol-main` из ZIP, новая версия не найдёт прежние тома. Чтобы этого не случилось, до обновления посмотрите имя проекта командой `docker compose ls` и впишите его в `.env`: `COMPOSE_PROJECT_NAME=<имя>`. Если `.env` нет, создайте его с этой одной строкой. Что делать, если обновление уже сделано: [«Если после обновления открылся мастер первого запуска»](#если-после-обновления-открылся-мастер-первого-запуска).

**Контейнер `ingestion` больше не нужен.** PDF теперь читает сам gateway, и `ingestion` сам не запускается. Уже запущенный можно убрать после обновления: `docker compose stop ingestion && docker compose rm -f ingestion`. Если в `.env` осталось `PDF_ENGINE=python`, а сервис не запущен, gateway читает PDF сам.

## Сервер, код скачан через git

```bash
cd med-control
git pull
docker compose up -d --build
docker compose up -d --force-recreate --no-deps edge
```

Последняя команда нужна, чтобы входная служба (edge) перечитала свой конфиг. Без неё она может остаться со старыми правилами. Пока gateway перезапускается (10–30 секунд: миграции, справочники), сайт отвечает ошибкой 502. Это нормально.

Если вместо сайта с данными открылся мастер первого запуска или `docker compose up` остановился с ошибкой о сети, см. [«Если после обновления открылся мастер первого запуска»](#если-после-обновления-открылся-мастер-первого-запуска).

## Сервер, код скачан архивом ZIP

1. Скачайте новый ZIP и распакуйте **рядом** со старой папкой.
2. Если в старой папке есть `.env`, скопируйте его в новую. На macOS и Linux файлы с точкой скрыты: `cp старая-папка/.env новая-папка/`.
3. В старой папке остановите службы (без `-v`, иначе данные сотрутся):

   ```bash
   docker compose down
   ```

4. В новой папке запустите:

   ```bash
   docker compose up -d --build
   ```

5. Откройте сайт и убедитесь, что данные на месте.
6. Прежде чем удалять старую папку, загляните в неё: если там есть папка `backups` с копиями, сначала перенесите её (см. [«С версии 0.2.0 или раньше»](#с-версии-020-или-раньше)). Без неё старую папку можно удалить: данные хранятся в томах Docker, копии лежат в `medcontrol-backups`.

Имя папки значения не имеет: проект Docker всегда называется `medcontrol`, и новая папка находит те же тома. Исключение: установка, сделанная версией 0.2.0 или раньше, см. следующий раздел.

## Если после обновления открылся мастер первого запуска

Так бывает при любом способе обновления, если установка сделана версией 0.2.0 или раньше из папки, которая называется не `medcontrol`: тома с данными названы по старой папке, а новая версия ищет проект `medcontrol`. Данные не пропали. Мастер в этой пустой установке не проходите.

При обновлении через git в той же папке вместо мастера `docker compose up` обычно останавливается с ошибкой `Pool overlaps with other one on this address space`: прежние контейнеры ещё работают, и новый проект не может создать свою сеть. Причина и лечение те же.

1. Остановите то, что успело запуститься под новым именем (без `-v`):

   ```bash
   docker compose down
   ```

2. Посмотрите старое имя проекта:

   ```bash
   docker volume ls | grep pgdata
   ```

   Имя стоит перед `_pgdata`, например `medcontrol-main`. Строка `medcontrol_pgdata`, если она есть, относится к новой пустой установке.
3. Впишите старое имя в `.env` строкой `COMPOSE_PROJECT_NAME=medcontrol-main` и запустите:

   ```bash
   docker compose up -d --build
   docker compose up -d --force-recreate --no-deps edge
   ```

## Synology (Container Manager)

1. Скачайте и загрузите новый код поверх старого в ту же папку через File Station. `.env` при этом не трогайте.
2. В Container Manager откройте проект medcontrol, остановите его, затем соберите заново и запустите (пункты меню проекта; названия зависят от версии DSM).

По SSH то же самое: команды из раздела «Сервер, код скачан через git», начиная с `docker compose up -d --build` (через `sudo`).

## Настольная версия

Установите новую версию поверх старой. Данные лежат в папке приложения, не рядом с программой, и при переустановке остаются.

## Откат на прошлую версию

Новая версия может оказаться неудачной. Вернуться можно так.

**Нужна ли копия базы.** Обычно прежняя версия работает с обновлённой базой: миграции добавляют таблицы и поля, а не убирают их. Тогда достаточно вернуть прежний код, и всё внесённое после обновления останется. Исключения отмечены в [CHANGELOG.md](../CHANGELOG.md) словами «откат только с восстановлением копии». Откат с 0.3.0 на 0.2.0 как раз такой: в 0.3.0 каждый приём препарата отмечается отдельно, и версия 0.2.0 не сможет записать приём в обновлённую базу. В таком случае, и если новая версия испортила данные, сначала верните базу к копии, сделанной перед обновлением, и только потом прежний код.

**Вернуть базу к копии (только если она нужна).** Всё, что внесено после этой копии, пропадёт. Копия, сделанная старой версией, не ложится поверх базы, которую уже обновила новая, поэтому база сначала пересоздаётся пустой. Команды выполняются в папке с новой версией, пока она ещё запущена. Они написаны для настроек по умолчанию; если в `.env` заданы свои `POSTGRES_USER` и `POSTGRES_DB`, подставьте их вместо `dtc`:

```bash
ls <папка с копией>/db.dump   # копия на месте
docker compose stop gateway frontend
docker compose exec -T postgres psql -U dtc -d postgres -c 'DROP DATABASE dtc WITH (FORCE)' -c 'CREATE DATABASE dtc'
docker compose exec -T postgres pg_restore -U dtc -d dtc --no-owner < <папка с копией>/db.dump
```

Вторая команда выключает сайт, третья стирает текущую базу, четвёртая заливает копию. Сайт не запускайте, пока не вернёте прежний код: новая версия при запуске снова обновит базу. Файлы, загруженные после обновления, останутся на диске, но записей о них в базе уже не будет.

**Вернуть прежний код.**

Через git:

```bash
git tag                       # список версий
git checkout v0.2.0           # версия, на которую возвращаетесь
docker compose up -d --build
docker compose up -d --force-recreate --no-deps edge
```

Из ZIP: остановите новую версию (`docker compose down`, без `-v`) и запустите старую папку (`docker compose up -d --build`).

После отката на 0.2.0 ночные копии снова ложатся в `backups` внутри папки с кодом, если в `.env` нет строки `BACKUP_DIR`.

Чтобы вернуться на свежую версию после отката через git: `git checkout main && git pull`, дальше как при обновлении.

## Для тех, кто разворачивает с рабочей машины

Скрипты `scripts/release.sh` и `scripts/deploy.sh` выкладывают версию на сервер по SSH. Они сами делают дамп перед обновлением, собирают образы с тегом и умеют откатываться за минуту без пересборки. Подробно в [OPERATIONS.md](OPERATIONS.md), раздел «Деплой».
