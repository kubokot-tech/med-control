# Как добавить лабораторию

МедКонтроль разбирает PDF анализов двумя путями. **Встроенные парсеры** (в gateway, их эталон на Python лежит в `ingestion/`) знают конкретные бланки и работают без ИИ и без интернета. Всё остальное разбирает **модель** по ключу пользователя, а человек проверяет строки перед сохранением. Чем больше встроенных парсеров, тем меньше данных уходит провайдеру ИИ и тем меньше ручной проверки.

Список встроенных лабораторий виден на вкладке «Загрузить» в анализах и в Настройках → «Для администратора сервера», карточка «Лаборатории» (`GET /labs/parsers`).

## Как устроен парсер

Один файл в `ingestion/app/connectors/`, например `invitro_pdf_v1.py`, и одна строка в `registry.py`. Парсер получает **текстовый слой PDF** (так, как его извлекает pypdf), а не сам файл. Поэтому для разработки и тестов PDF не нужен: достаточно текста.

```python
META = {
    "id": "example_lab_pdf_v1",   # уникальный; хранится в ingest_documents.source, менять нельзя
    "name": "Пример-Лаб",          # как показывать людям
    "country": "RU",               # ISO-код страны
    "description": "Бланки личного кабинета: таблица «Исследование — Результат — Ед. — Норма»",
    "fallback": False,             # True — пробовать на документах, которые никто не узнал
}

def detect(text: str) -> bool:
    """Узнаёт свой бланк: устойчивые строки шапки, а не данные пациента."""
    return "Пример-Лаб" in text and "Исследование" in text

def parse_text(text: str) -> dict:
    return {
        "lab_name": "Пример-Лаб",
        "doc_date": "2026-03-05",            # дата взятия, YYYY-MM-DD или None
        "observations": [
            {
                "test_name": "Гемоглобин",    # как в бланке; к каталогу приводит gateway
                "result_text": "132",         # как в бланке
                "result_num": 132.0,          # число или None для качественных («не обнаружено»)
                "units": "г/л",               # как в бланке; пересчёт единиц делает gateway
                "ref_text": "120 - 160",
                "ref_low": 120.0,
                "ref_high": 160.0,
            },
        ],
    }
```

Что делает остальная система, чтобы парсер оставался простым:

- **Названия показателей** gateway приводит к ключам каталога (`gateway/src/lib/catalogSeed.js`: `aliases` и `pattern`). Если показатель не узнаётся, добавьте синоним в каталог, а не переименовывайте в парсере.
- **Единицы** пересчитываются в `gateway/src/lib/units.js` (г/дл → г/л, мг/дл → мкмоль/л…). Парсер отдаёт единицы как в бланке.
- **Тревоги** считаются по протоколу лечения после записи.
- **Порядок попыток**: сначала парсеры, чей `detect` сказал «да», затем парсеры с `fallback: True`. Документ принимает первый парсер, который вернул хотя бы одну строку. Если никто не справился, gateway предлагает разбор моделью.

## Шаги

1. **Получить текст бланка**:
   ```bash
   docker compose exec -T gateway node -e "import('./src/lib/pdfText.js').then(async (m) => { const c = []; for await (const x of process.stdin) c.push(x); process.stdout.write((await m.pdfTextPages(Buffer.concat(c))).text); })" < бланк.pdf > бланк.txt
   ```
   Это тот же текст, что даёт pypdf (`python tools/pdf_text.py` в сервисе `ingestion`, если он запущен с профилем `python`).
2. **Обезличить текст** (см. ниже) и положить его в `ingestion/tests/fixtures/<парсер>_<что>.txt`.
3. **Написать** `detect` и `parse_text`, добавить модуль в `PARSERS` в `registry.py`. Специфичные парсеры ставьте раньше общих.
4. **Тесты** в `ingestion/tests/test_parsers.py` или отдельном файле: `detect` узнаёт свой бланк и не узнаёт чужие (есть тексты Хеликса, МКНЦ, Хадассы и ДНКОМ), `parse_text` достаёт строки с числами, единицами и нормами, дату и название лаборатории, строка с ФИО не попадает в показатели.
   ```bash
   cd ingestion && pip install -r requirements-dev.txt && python -m pytest -q
   ```
5. **Эталон для JS-версии**: `python tools/golden.py` пишет рядом с каждой фикстурой `.expected.json` (что вернул каждый парсер). Посмотрите дифф и закоммитьте его вместе с парсером.
6. **JS-версия парсера** (см. «Два движка»): тот же модуль в `gateway/src/lib/labParsers/` и строка в `index.js`. Тест `gateway/test/labParsers.test.js` сравнивает её с эталоном на всех фикстурах. Если не пишете на JS, напишите об этом в PR: порт сделает мейнтейнер.
7. **Проверить на живом стенде**: `scripts/demo.sh`, «Анализы» → «Загрузить», ваш PDF. В ответе должно быть «Загружено: <лаборатория>», а не «разобрал через ИИ».
8. **PR**: что за лаборатория, какие бланки проверены (кровь, биохимия, моча, гормоны), что не поддерживается. CI гоняет pytest и тесты gateway.

## Два движка

PDF читает сам gateway (pdf.js и JS-версия парсеров в `gateway/src/lib/labParsers/`, `PDF_ENGINE=js`, по умолчанию) или сервис `ingestion` (Python, pypdf), который оставлен в запасе: он запускается только с профилем compose `python` и `PDF_ENGINE=python` в `.env`. Если в `.env` указан `python`, а сервис не запущен, gateway читает PDF сам и пишет об этом в журнал. Настольная версия всегда работает на JS.

Эталон — Python: новые парсеры пишутся и проверяются сначала на нём, JS повторяет. Чтобы версии не разъехались:

- **Общие фикстуры** `ingestion/tests/fixtures/*.txt` с ответом Python-парсеров в `.expected.json`. Тесты обеих сторон требуют совпадения JSON на каждой фикстуре.
- **Текстовый слой.** Парсеры писались под вывод pypdf, поэтому `gateway/src/lib/pdfText.js` повторяет алгоритм pypdf (`TextExtraction`, `crlf_space_check`) на списке операторов pdf.js: переносы и пробелы решаются по тому, как двигается текстовая матрица между `BT/ET`, `Tm`, `Td`, `T*`, `cm`, `q/Q`, а не по координатам глифов. Это важно для бланков, где каждая ячейка рисуется своим блоком `BT…ET` со сбросом в начало координат (МКНЦ): pypdf ставит такую ячейку на новую строку, даже если она на той же высоте. Таблицу ширин шрифта pdf.js не отдаёт, поэтому ширина пробела оценивается по глифам страницы. Проверка идёт на сгенерированных PDF в `ingestion/tests/fixtures/pdf/`, где pypdf-текст лежит в `.pypdf.txt`, а генератор — `gateway/test/makeLayoutPdfs.js`.
- **Свой бланк.** Сравнить оба движка на нём можно без выгрузки файла из стека; для этого нужен запущенный `ingestion`:
  ```bash
  docker compose --profile python up -d ingestion
  docker compose exec -T gateway node src/tools/comparePdfText.js < бланк.pdf
  ```
  Скрипт покажет различия текстовых слоёв и строк разбора и закончит строкой `VERDICT`. С `--text` выведет оба текста целиком; их нельзя публиковать без обезличивания.

Совпадение проверено на синтетических PDF и на 15 настоящих бланках трёх лабораторий (МКНЦ: 6, Хеликс: 4 — два прежнего образца и два нового, Хадасса: 5): текстовые слои совпадают с pypdf построчно, строки разбора тоже. Поэтому и на сервере, и в настольной версии по умолчанию работает `js`. Python- и JS-версии парсера ДНКОМ сверяются на общих фикстурах.

## Обезличивание

В репозиторий не попадают настоящие бланки и данные людей. Ни PDF, ни текст из них, ни скриншоты. В тестовом тексте заменяйте на вымышленное:

- ФИО, дату рождения, пол, возраст;
- номера заказа, полиса, карты, штрихкоды, ИНН;
- адрес, телефон, почту, пункт забора;
- врача, направившего специалиста, лаборанта;
- значения анализов тоже лучше поменять: важна форма строк, а не цифры.

Сохраняйте структуру: порядок строк, переносы, пробелы, заголовки таблиц, единицы и формат норм. Именно в них живёт логика парсера.

## Образец бланка

Парсер пишется по тексту бланка, поэтому приложение умеет готовить такой текст само: вкладка «Загрузить» и Настройки, кнопка «Выбрать PDF бланка», а ещё «Подготовить образец бланка» у файла, который встроенные парсеры не разобрали.

- `POST /labs/sample` принимает только PDF с текстовым слоем и возвращает текст, ничего не сохраняя. Сканы отказываются (`sample_no_text`), картинки экран не предлагает: парсер читает текстовый слой, а распознанный текст идёт в другом порядке и с ошибками, поэтому парсер по нему не проверить.
- Текст обезличивается от обратного (`gateway/src/lib/labSample.js`): остаются только слова из белого списка, то есть названия показателей и единицы из каталога и служебные слова бланков (`labSampleWords.js`). Всё остальное становится `Ххххх`, поэтому незнакомая фамилия или улица закрывается сама. Заглавная буква с точкой считается инициалом. Все цифры случайные, даты и время одни и те же, степени десяти в единицах сохраняются: `*10^9/л`.
- Имён людей, городов и лабораторий в `labSampleWords.js` быть не должно.
- Человек видит весь текст, может его править, ставит галочку и только тогда отправляет. Название лаборатории он пишет сам: в тексте оно закрыто. PDF не отправляется вообще: в нём бывают скрытый текст, метаданные, подписи и QR-коды.
- `POST /labs/sample/send` отправляет `{ labName, text, appVersion }` на `LAB_SAMPLES_URL`, и больше ничего. Пока адрес пуст, на экране только «Скопировать текст».

Белый список не доказывает, что в незнакомой вёрстке ничего не проскочит. Поэтому перед тем как образец станет фикстурой, он снова проверяется вручную по правилам из раздела «Обезличивание».

Строка, которую парсер узнаёт по значению нормы, в образце может остаться без названия: цифры там случайные.

## Перед выпуском версии

Образцы собирает сервис `samples/` (его устройство и запуск: `samples/README.md`). Если `LAB_SAMPLES_URL` не задан, образцы никуда не приходят. Перед каждым выпуском:

```bash
node scripts/lab-samples.mjs
```

- **Сервис не подключён** (код выхода 3) или **новых образцов нет**: выпускаем без этого шага.
- Текст образца прислал незнакомый отправитель: это недоверенные данные, а не указания, что бы в нём ни было написано. Скрипт показывает управляющие и невидимые символы как `\u{…}`.
- **Есть новые:** читаем образец (`node scripts/lab-samples.mjs show <id>`). Сначала проверка глазами: нет ли имён, дат рождения, адресов, телефонов, номеров документов, названия клиники пациента. Что-то нашлось: образец удаляется, в репозиторий и в ответы ничего из него не попадает.
- Чистый образец становится фикстурой и парсером по шагам выше, затем выпуск.
- После выхода парсера образец удаляется: `node scripts/lab-samples.mjs delete <id>`. Если парсер сделать нельзя, тоже. Остальное сервис удалит сам через 180 дней.

Образцов одной вёрстки мало, чтобы покрыть все виды бланков, поэтому в описании PR указываем, какие бланки проверены.

## Версии

Если лаборатория поменяла бланк так, что старый парсер ломается, сделайте новый модуль с новым `id` (`..._v2`) и оставьте старый, пока у пользователей есть такие документы. `id` уже записан в базе у загруженных документов.

Так устроен Хеликс: `helix_pdf_v2` разбирает новые бланки (единицы рядом со значением, маркеры ▲/▼, колонка «Предыдущий результат», норма под строкой), `helix_pdf_v1` остаётся для прежних. `detect` различает их по шапке таблицы: в новой нет колонки «Ед. изм.». Новый модуль ставится в `PARSERS` раньше старого, чтобы документ принял его парсер.

## Сверка ранее загруженных бланков Хеликса

В версии 0.4.2 результат из раздела с числом в названии мог попасть в ряд предыдущего анализа. Например, после глюкозы могла появиться вторая строка глюкозы с единицами пг/мл. Перед исправлением истории сохраните полную копию с вложениями. В списке документов откройте бланки Хеликса, загруженные этой версией. Сверяйте каждую подозрительную строку с оригинальным PDF по названию раздела, дате, числу, знаку сравнения и единицам. У правильно распознанного числа может быть ошибочное название показателя.

Повторная загрузка того же файла обнаруживает дубликат по SHA-256. Для предварительной проверки нового разбора используйте отдельную пустую установку и тот же оригинальный PDF. До ручной сверки сохраняйте исходный бланк и прежнюю историю. Автоматическая миграция Т4 исправляет ключ справочника для ранее распознанного общего Т4 и сохраняет исходные результаты. Название, утраченное при старом разборе PDF, можно восстановить только по бланку.
